# 故障排查

| 症状 | 检查与处理 |
| --- | --- |
| 没有 cu.usbmodem | 确认原生 USB 口、数据线；CH343P 通常是另一个端口；完全断开目标后手动 BOOT+RESET 进下载模式 |
| flashrom 无响应/握手异常 | 关闭 idf monitor、串口工具；复位 ESP 后重新解锁，核对端口；不要同时运行两个读取进程 |
| output drivers / SPI 操作 NAK | 是否先松开 BOOT 再按住两秒？是否是只读不允许的 opcode？查 -VV 日志，禁止关闭白名单或强制执行 |
| 无法识别、ID 为 00/FF | 停止读取，断电核对夹子方向、触点、GND、供电及 STM32 高阻；不能一边带电挪夹子一边重试 |
| 多个芯片名称 | 核对丝印/数据手册/JEDEC ID，再指定精确 -c 名称；默认 W25Q128.V 只是常见映射 |
| 检测到其他容量/1.8 V 型号 | 不继续，不加 -f，重新核对实物与电压 |
| 读取被拒绝（复位、唤醒、状态写等） | 有些 flashrom 版本或芯片入口会尝试状态修改；保留日志，评审具体事务；不要放行非读取命令 |
| 500 kHz 仍有差异 | 查总线争用、VCC 纹波、夹子接触、接地、线长；换新输出目录重试，保留失败文件 |
| 全 00/FF 且两份一致 | 不通过；一致不等于真实内容，先排电气和夹子问题 |
| 输出 .partial | 读取未通过；看对应日志；脚本不会覆盖旧目录，从新目录重新读取 |
| SHA256SUMS 有但无 VERIFIED.txt | 流程未完整结束；独立运行 verify_dumps.py，不凭单个文件名认定成功 |
| macOS flashrom 权限错误 | 核对串口是否被占用和安装情况；通常原生串口不需要 sudo，不先盲目提权 |
| 命令行提速但速度不变 | 默认固件硬上限 500 kHz；查日志实际频率，参考重新配置/编译步骤 |
| BOOT 后设备进入下载模式 | BOOT 是复位采样脚，不能按住它复位来“解锁”；先松开并复位进应用，再按两秒 |
| 目标板异常发热/电流增大 | 立即按受控顺序停止并断电；不要靠限频继续读取；重新评估反灌/共轨/争用 |

本项目没有自动发起硬件探测、复位目标 STM32、切换目标供电或修改 Flash 模式的功能。
USB 断连/主机崩溃后，不能保证立刻自动停止所有引脚输出；先按既定安全方案停止会话，
必要时物理隔离，完成后复位 ESP。固件会话解锁保持到 ESP 复位。

## 本地与 CI 检查

```bash
cc -std=c11 -Wall -Wextra -Werror tests/test_policy.c -o /tmp/test-policy
/tmp/test-policy
python3 tests/run_protocol_test.py
python3 -m unittest discover -s tests -v
bash -n scripts/build_macos.sh scripts/flash_macos.sh
```

GitHub Actions 使用 ESP-IDF v6.0 编译 ESP32-S3，并上传构建产物。
CI 成功只证明构建与软件测试，不能证明你的芯片夹接触、目标供电和实物读取成功。
首次烧录后，应先在不接目标时验证：锁定状态拒绝输出使能；再通过带保护的测试环境/
逻辑分析仪验证解锁、500 kHz 和 SPI 白名单。不要在原玩具上试发破坏性命令来测试拦截。
